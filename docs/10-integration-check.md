## 1. 점검 환경

| 항목 | 값 |
|---|---|
| 백엔드 | `node --env-file=.env.test src/server.js`, 포트 3109, `LOG_LEVEL=warn` |
| 데이터베이스 | **`clubhome_test`** (테스트 DB) |

`resize_window`가 이 환경에서 탭 뷰포트에 반영되지 않아, 같은 페이지를 지정 폭 `iframe`에 띄워 측정했다. 미디어쿼리는 iframe 뷰포트를 기준으로 평가되므로 실제 폭 전환과 같은 결과가 나온다.

## 3. 거부 케이스 집중 점검

이슈가 지정한 4종을 포함해 9종을 확인했다. **화면에서 버튼을 감춘 것과 서버가 실제로 막는 것을 따로 확인했다** — 버튼을 숨겼다는 이유로 서버 검증에 기대지 않는다는 원칙(§2.1)의 검증이다.

| 거부 케이스 | 화면 | 서버 직접 호출 |
|---|---|---|
| 등급 미달 게시판 접근 | 자물쇠 + "접근불가" 표시 | `403` "이용 권한이 없는 게시판입니다." |
| 중복 예약 (부분 겹침) | 409 안내 + "최신 예약현황 보기" | `409` "이미 예약된 시간대가 포함되어 있습니다." |
| 운영시간 밖 예약 | 400 안내 | `400` "운영시간(09:00~22:00) 내에서만" |
| 시작 후 예약 취소 | 취소 버튼 미노출 | `403` "이미 시작된 예약은 취소할 수 없습니다." |
| 타인 예약 취소 | 목록에 애초에 없음 | `403` "본인 또는 관리자만 예약을 취소할 수 있습니다." |
| 타인 게시글 수정 | 수정 버튼 미노출 | `403` "본인 또는 관리자만 수정·삭제할 수 있습니다." |
| 타인 게시글 삭제 | 삭제 버튼 미노출 | `403` (동일 문구) |
| 비관리자 관리자 경로 | 홈으로 리다이렉트, `[관리자]` 메뉴 없음 | (모든 `/api/admin/*`가 서버에서 `is_admin` 검사) |
| 참조 중인 항목 삭제 | 409 안내 + **비활성 경로 안내** | `409` "게시글이 있는 게시판은 삭제할 수 없습니다." / "예약 이력이 있는 연습실은…" |

**BE-11 축소분 대체 점검** — 이슈가 요구한 "자동화에서 빠진 인증·소유권 항목"에 해당하는 것은 위 표의 소유권 4종(타인 예약 취소, 타인 게시글 수정·삭제, 시작 후 취소)과 인증 3종(재발급, Refresh 만료 시 로그아웃, 비관리자 차단)이다. 모두 서버 응답까지 확인했다.

## 4. 반응형 레이아웃 실측

10개 화면을 모바일 390px와 PC 1280px 두 폭에서 측정했다. **모든 화면에서 가로 스크롤 넘침이 0px**이다.

| 폭 | 네비게이션 | 표 위주 화면 |
|---|---|---|
| 390px | 햄버거 `display: grid`, 가로 메뉴 숨김 | 열 제목 숨김 → 카드 리스트 |
| 1280px | 가로 메뉴 `display: flex`, 햄버거 숨김 | 열 제목 `display: grid` → 표 |

점검한 경로: `/`, `/boards`, `/boards/:id/posts`, `/me`, `/me/reservations`, `/practice-rooms`, `/admin`, `/admin/members`, `/admin/boards`, `/admin/practice-rooms`.

관리자 화면은 와이어프레임 §1의 결정대로 모바일에서 표를 카드로 바꾸지 않고 세로로 쌓는다. 이 경우에도 페이지 본문이 좌우로 스크롤되지 않는 것을 확인했다.

접근성 점검은 범위 밖이다(PRD §3 Out of Scope).

## 5. 발견 결함

**P0 기능을 막는 결함 0건.**

### P0가 아닌 발견 1건 — 기록만 남긴다

**과거 날짜로 예약을 만들 수 있다.** 서버가 예약 신청에서 30분 경계·시간 순서·운영시간·중복은 검증하지만 **날짜가 과거인지는 보지 않는다**(`backend/src/services/reservation-service.js`). 프론트엔드의 날짜 입력에도 하한이 없다.

이 점검에서 "시작 후 취소는 403" 케이스를 만들기 위해 일부러 이 경로를 썼다 — 과거 날짜 예약을 만든 뒤 취소를 시도해 403을 확인했다. 즉 점검 도구로는 유용했지만, 사용자가 어제 날짜를 골라 예약할 수 있다는 뜻이기도 하다.

P0 기능을 막지 않으므로 이슈 IT-01의 "P0 영향 항목만 우선 수정" 방침에 따라 고치지 않고 기록만 남긴다. 고칠 때의 선택지는 두 가지다.

- 프론트: 날짜 입력에 `min`을 오늘로 준다. 화면에서 고를 수 없게 되지만 주소를 직접 고치면 통과한다.
- 백엔드: `createReservation`에서 과거 날짜를 400으로 거절한다. 실제 차단은 이쪽이어야 한다(원칙 §2.1 — 최종 판정은 서버).

양쪽을 함께 하는 것이 이 프로젝트의 다른 검증과 일관된다.

### 이번 점검에서 재확인된 기존 수정

FE-01~FE-09 진행 중 각 이슈의 소스 리뷰와 브라우저 확인 단계에서 결함 13건을 찾아 그 시점에 고쳤고, 그 수정들이 이번 통합 점검에서 함께 재확인됐다. 그중 통합 점검이 직접 재확인한 항목은 다음과 같다.

- 게시글 수정 시 조회수가 오르지 않는다(FE-06 수정분) — S-04에서 조회수 1 유지 확인
- 등급 변경 성공 안내가 표시된다(FE-09 수정분) — S-07에서 "등급을 변경했습니다." 확인
- 보호 경로의 쿼리 문자열이 로그인 후 복원된다(FE-03 수정분) — 자동화 테스트로 고정

## 6. 확인하지 못한 항목

정직하게 남긴다. 이후 점검이나 운영에서 다시 볼 지점이다.

- **Access Token 자연 만료.** 유효기간이 `.env`의 `JWT_ACCESS_EXPIRES_IN`으로 정해져 있어 실시간으로 기다릴 수 없었다. 대신 저장된 토큰을 훼손해 401을 유발하는 방식으로 재발급 경로를 확인했다. 서버가 만료 토큰과 위조 토큰을 같은 401로 처리하므로 같은 경로를 타지만, "시간 경과로 인한 만료"를 그대로 재현한 것은 아니다.
- **동시 예약 경합.** 두 계정이 정확히 같은 순간에 같은 구간을 신청하는 경우다. 순차 시도로 409를 확인했고, 원자성 자체는 백엔드의 트랜잭션 + 부모 행 잠금과 `backend/tests/`가 담당한다.
- **게시글 페이지네이션 2페이지 이상.** 테스트 DB에 20건 이상 글이 없어 실제로 페이지를 넘겨보지 못했다. 페이지 이동·번호 계산·범위를 벗어난 페이지는 자동화 테스트로 고정돼 있다.
- **HTTPS 환경.** 점검은 `http://localhost`에서 했다. 운영 HTTPS 전환은 IT-02 범위다.
- **다른 브라우저.** Chrome만 확인했다.

## 7. 재현 절차

같은 점검을 다시 하려면 아래 순서를 따른다.

```bash
# 1. 테스트 DB 준비 (backend/README.md 참조)
cd backend && npm run test:db

# 2. 백엔드 (테스트 DB, 프론트 origin 허용)
CORS_ORIGIN=http://localhost:5199 PORT=3109 LOG_LEVEL=warn \
  node --env-file=.env.test src/server.js

# 3. 프론트엔드
cd frontend && VITE_API_BASE_URL=http://localhost:3109 \
  npm run dev -- --port 5199 --strictPort
```

점검 중 만든 회원·예약·게시글은 테스트 DB에만 남는다. 점검용으로 만든 게시판·연습실은 참조가 없으면 삭제하고, 참조가 생겼으면 사용여부를 비활성으로 두면 된다.

**개발 DB로 점검하지 않는다.** 시나리오가 회원·게시글·예약을 실제로 만들기 때문에 개발 데이터가 오염된다.

### 주의: 시드 회원의 등급을 바꾸면 백엔드 테스트가 깨진다

이번 점검에서 실제로 밟은 함정이다. S-07(등급 변경)을 확인하려면 대상 회원이 필요한데, 시드 회원 `junior1@clubhome.local`의 등급을 정회원으로 올렸다. 그 뒤 `cd backend && npm test`를 돌리자 **233건 중 68건이 실패**했다 — `tests/board-api.test.js`가 `시드 junior1은 준회원(10)이어야 한다`를 전제로 등급별 접근 제어를 검증하기 때문이다.

백엔드 테스트와 통합 점검이 **같은 테스트 DB를 공유**하고, 테스트 쪽은 시드 상태를 사실로 전제한다. 따라서 등급 변경 같은 시드 데이터 수정은

- 점검용으로 **새로 가입한 회원**을 대상으로 하거나,
- 부득이 시드 회원을 썼다면 점검 후 `docs/seed-dev.sql`의 등급으로 되돌려야 한다.

시드 등급은 `admin=30 / senior=20 / junior1=10 / junior2=10`이다. 되돌린 뒤 백엔드 233건이 모두 통과하는 것을 확인했다.
