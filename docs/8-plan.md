## 0. 문서 개요
본 문서는 docs 디렉토리의 기획·설계 문서(도메인 정의서, PRD, 사용자 시나리오, 와이어프레임, 프로젝트 구조 설계 원칙, 아키텍처 다이어그램, ERD, `schema.sql`, `seed-dev.sql`)를 근거로 실제 구현 작업을 데이터베이스·백엔드·프론트엔드 단위의 독립 Task로 분해한 실행 계획이다.

## 1. 계획 수립 기준

- **범위**: PRD §4의 **P0 기능**(F-01~03, F-10~12, F-20~22, F-30~32)을 2일 내 완성 대상으로 한다. P1(F-04 계정상태 자동전이, F-23 예약 자동완료)은 §7 백로그로 분리한다.
- **제외**: 자료실(도메인 정의서 v0.2에서 범위 제외), 네이티브 앱, 알림/결제, 접근성 대응(PRD §3 Out of Scope).
- **리소스**: 1인 개발, 2일.
- **Task 분해 원칙**: 각 Task는 독립적으로 착수·완료·검증이 가능한 단위로 나누되, 레이어 원칙(routes→controller→service→repository)에 따라 하나의 기능(F-ID)을 세로로 관통해 완성한다. 레이어별 가로 분해(예: "모든 controller 작성")는 중간 산출물이 검증 불가하므로 하지 않는다.
- **Task ID**: `DB-nn`(데이터베이스), `BE-nn`(백엔드), `FE-nn`(프론트엔드), `IT-nn`(통합/마무리).

### BE-03. 회원가입·로그인·로그아웃·토큰 재발급 API (F-01, F-02)

- **수행 작업**
  - `POST /api/auth/signup`: 필수값·이메일 형식 검증, 이메일 중복 확인, 비밀번호 해시 저장, 기본 등급(최저 `grade_level`) 부여

  - `POST /api/auth/logout`: 클라이언트 토큰 폐기 기준 처리(서버 측 토큰 저장소 없음 - ERD §4)

  - [x] 중복 이메일 가입이 409(또는 400)로 거부된다

  - 보호 경로는 `/boards`·`/practice-rooms`·`/me`·`/admin` 넷이다. swagger에서 `security: []`인 것은 signup·login·refresh뿐이므로 나머지 화면은 로그인 없이 열면 401만 받는 빈 화면이 된다. 등급·관리자 기준의 세부 차단은 각 화면 이슈와 서버 403이 담당하고, 여기서는 로그인 여부만 본다.
  - 로그아웃은 확인 응답용 `POST /api/auth/logout` 실패와 무관하게 토큰을 폐기한다(`onSettled`). 서버에 토큰 저장소가 없어 폐기의 실체가 클라이언트 삭제이므로, 요청 실패로 로그아웃을 막으면 네트워크가 끊긴 상태에서 로그아웃할 방법이 없어진다. 함께 TanStack Query 캐시도 비운다 — 이전 사용자의 서버 데이터가 남으면 다음 로그인 직후 그것이 보인다.
  - **알려진 한계**: `authStore.isAdmin`은 로그인 시점 값이고 토큰 재발급 시 갱신되지 않는다(재발급 응답이 `accessToken`만 준다). 관리자 등급이 변경된 회원은 재로그인 전까지 이전 메뉴를 보게 되지만, 표시 제어일 뿐이고 실제 인가는 서버 403이 막는다.

## 8. 계획 외 추가 구현 (BE-11 이후)

아래는 §2 Task 목록에 없었으나 BE-01~BE-11 완료 후 요청에 따라 구현된 항목이다. **P0 기능(F-ID)을 늘리지 않는 운영·검증 보강**이며, 새 Task로 번호를 부여하지 않고 여기에 기록만 남긴다. 각 항목의 사용법은 `backend/README.md`에 있다.

| 항목 | 내용 | 신규 의존성 | 관련 원칙 |
|---|---|---|---|
| 콘솔 로깅 | `utils/logger.js`. 기동·모든 요청/응답·거부 사유·트랜잭션 롤백 4지점. `LOG_LEVEL`로 조절하며 `node --test` 하위에서는 기본 `silent` | 없음 | §5 로깅 |

| 헬스체크 503 | DB 연결 실패 시 200 대신 503. 상태코드만 보는 프로브로 장애를 감지할 수 있게 한다 | 없음 | §5 헬스체크 |

**IT-01과의 관계**: 위 E2E는 API 계층만 덮으므로 IT-01("브라우저에서 S-01~S-08 수동 확인")을 대체하지 않는다. 다만 IT-01 착수 전에 백엔드 쪽 결함을 걷어내는 용도로 쓸 수 있다.

**IT-02와의 관계**: `CORS_ORIGIN` 주입 수단이 생겼으므로 IT-02 완료조건 중 "운영 환경에서 CORS 허용 origin이 환경변수로 주입된다"는 구현 측 준비가 끝났다. 다만 `ENABLE_API_DOCS`는 운영에서 **끄는** 것이 기본값이라는 점을 배포 절차에 포함해야 한다.
