# 색연필 색소폰 동호회 홈페이지 - PRD (제품 요구사항 정의서)

## 0. 문서 개요
본 문서는 색소폰 동호회 "색연필" 홈페이지의 제품 요구사항을 정의한다. 도메인 정의서(`docs/1-domain-definition.md`, v0.6)의 엔티티(회원, 회원등급, 게시판/게시글, 연습실, 예약)와 비즈니스 규칙을 기반으로 하며, 여기에 실제 개발을 위한 비즈니스/기술/일정 제약을 결합해 실행 가능한 요구사항 형태로 구체화한다.

## 1. 배경 및 목표

### 1.1 문제 정의
현재 "색연필" 동호회는 회원 관리, 공지/소통, 연습실 예약을 비공식 채널(문자, 구두, 수기 장부 등)로 처리하고 있어 다음 문제가 발생한다.
- 연습실 예약 중복/누락 확인이 어려움
- 등급(준회원/정회원/운영진 등)에 따른 정보 공유 범위를 통제할 수단이 없음
- 회원 정보와 이력이 개인 채널에 흩어져 관리되지 않음

### 1.2 비즈니스 목표
- 회원가입/로그인 기반의 단일 홈페이지에서 회원관리, 게시판, 연습실 예약을 일원화
- 동시 접속 20명 규모의 소규모 커뮤니티 운영을 안정적으로 지원
- 관리자가 등급/게시판/연습실을 직접 운영할 수 있는 최소한의 관리 기능 제공

## 2. 대상 사용자
- 주 사용자: 직장인 중심의 동호회 회원 (전체 500명 이하 규모)
- 페르소나: 퇴근 후 스마트폰/PC로 짬짬이 접속해 공지 확인, 연습실 예약을 하는 일반 회원 1종과, 등급/게시판/연습실을 관리하는 운영진(관리자) 1종으로 충분하다. 별도의 상세 페르소나 시나리오는 작성하지 않는다.

## 3. 범위

### In Scope
- 회원가입/로그인/로그아웃, 본인 정보 수정
- 회원등급 체계 및 등급별 게시판 접근 제한
- 게시판/게시글 CRUD (등급 기반 열람/작성 제한 포함)
- 연습실 등록/관리, 예약 현황 조회, 예약 신청/취소
- 관리자 메뉴: 회원등급 관리, 게시판 관리, 연습실 관리

### Out of Scope
- 자료실 기능 (도메인 정의서 v0.2에서 제외 확정)
- 네이티브 모바일 앱
- 결제/전자상거래, 알림(이메일/문자/푸시) 발송, 소셜 로그인 등 부가 기능
- 접근성(웹 접근성 표준 준수) 대응

## 4. 기능 요구사항

우선순위: **P0**(2일 내 필수 MVP), **P1**(MVP 이후 확장)

### 4.1 회원관리
| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| F-01 | 회원가입 | 이름/이메일(로그인ID)/비밀번호/연락처 입력, 신규 회원은 기본 등급 부여 | P0 |
| F-02 | 로그인/로그아웃 | 이메일+비밀번호 인증 후 JWT Access/Refresh Token 발급, Access Token 만료 시 Refresh Token으로 재발급, 로그아웃 시 클라이언트에 저장된 토큰 폐기(서버 측 토큰 저장소는 두지 않음 - ERD §4 참고) | P0 |
| F-03 | 본인 정보 수정 | 로그인 회원이 연락처 등 본인 정보 수정 | P0 |
| F-04 | 계정상태 관리 | 활성/휴면/탈퇴 상태 반영, 탈퇴 회원은 로그인 불가하되 게시글/예약 이력은 보존 | P1 |

## 5. 비기능 요구사항
- **동시 접속**: 20명 동시 사용 시 정상 응답 (전체 회원 규모 500명 이하 기준)
- **성능**: 목록/조회 API 응답 1~2초 이내 목표 (별도 캐시/CDN 등 인프라 투자 없이 달성 가능한 수준)
- **가용성**: 별도 이중화 없이 단일 서버 운영을 전제로 하며, 동호회 활동 시간대(저녁/주말)에 서비스 가능한 수준이면 충분
- **보안**: 비밀번호는 해시 저장, 등급별 접근제어(인가) 적용. 별도의 침투테스트/보안감사는 범위 외
- **접근성**: 접근성 요구사항 없음 (WCAG 등 표준 준수 대응하지 않음)
- **데이터 보존**: 탈퇴 회원의 게시글/예약 이력은 삭제하지 않고 보존

## 6. 기술 스택 및 제약사항
- **프론트엔드**: React 19 + TypeScript, 상태관리 Zustand, 서버상태/캐싱 TanStack Query
- **백엔드**: Node.js + JavaScript + Express, DB 접근은 `pg` 라이브러리 기반 순수 SQL/쿼리빌더 사용 (Prisma 등 ORM 사용 금지)
- **데이터베이스**: PostgreSQL 17
- **인증**: JWT 기반, Access Token(단기, 예: 15분~1시간)과 Refresh Token(장기, 예: 7~14일)을 함께 사용. Access Token 만료 시 Refresh Token으로 재발급. JWT Secret과 각 토큰 유효기간은 코드에 하드코딩하지 않고 환경변수(예: `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `JWT_ACCESS_EXPIRES_IN`, `JWT_REFRESH_EXPIRES_IN`)로 관리. 별도 OAuth/소셜 로그인 없음

## 7. 플랫폼 및 UX 전략
- 웹 우선 개발, 모바일 전용 네이티브 앱은 만들지 않음
- 반응형 웹 UI로 PC/모바일 브라우저 모두 대응
- 별도의 디자인 시스템/컴포넌트 라이브러리 신규 구축 없이 실용적인 최소 UI로 구성

## 8. 일정 및 리소스
- **팀 구성**: 1인 개발 (기획~개발~배포 전 과정)
- **일정**: 2일 (아래는 우선순위 기반의 현실적 진행안이며 시간 배분은 진행 중 조정 가능)

| 구분 | 범위 | 비고 |
|---|---|---|
| 2일 내 필수 (P0) | F-01~03, F-10~12, F-20~22, F-30~32 | 회원 인증, 등급기반 게시판, 예약 신청/취소, 관리자 기본 CRUD까지가 MVP |
| 이후 확장 (P1) | F-04(계정상태 자동 전환), F-23(예약 자동 완료 처리) | 배치/스케줄러성 로직으로 MVP 이후 여유 시 추가 |

- **예산**: 1인 개발 규모에 준함 (별도 항목 상세화 없음)

## 9. 리스크 및 가정사항
- 1인 개발·2일 일정 특성상 테스트/QA는 핵심 시나리오(로그인, 등급별 게시판 접근, 예약 중복 방지) 중심의 최소 검증에 그친다.
- 계정상태 자동전이(휴면/탈퇴)와 예약 자동완료 등 배치성 로직은 P1로 미루며, MVP에서는 관리자 수동 처리로 대체 가능하다고 가정한다.
- 동시접속 20명 목표는 별도 부하테스트 없이 일반적인 소규모 웹앱 구성으로 충족 가능하다고 가정한다.
- 요구사항 변경 시 도메인 정의서(1-domain-definition.md)와 본 PRD를 함께 갱신해 정합성을 유지한다.
